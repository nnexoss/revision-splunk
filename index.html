01

Concepts et architecture

Sources : splunk-quick-reference-guide.pdf, module 7

Le vocabulaire de base

Event
Un ensemble de valeurs associées à un horodatage. Une entrée de données, sur une ou plusieurs lignes (une ligne de log, une stack trace…).
Index
L'endroit sur disque où sont stockés les events. Par défaut : main. Index internes : _internal, _audit, _introspection, _metrics, summary, history…
host
Le nom de la machine (physique ou virtuelle) d'où vient l'event.
source
Le fichier, répertoire, flux ou port d'où vient l'event (ex. /var/log/messages, UDP:514).
sourcetype
Le format de la donnée (ex. access_combined, linux_secure). Des sources différentes peuvent partager le même sourcetype.
Field
Une paire nom = valeur interrogeable (status=503, host=www1).
Tag
Un nom descriptif posé sur une paire champ = valeur pour regrouper ou rendre lisible.
Metric
Timestamp + nom de métrique + mesure (numérique) + dimensions. Stocké dans un index différent des events.
App
Une collection de configurations, knowledge objects, vues et dashboards (ex. Search & Reporting).

Index-time et search-time

À l'indexation, Splunk lit la donnée, lui attribue host, source et sourcetype, extrait le timestamp, découpe en events (règles de line-breaking) et écrit dans un index. À la recherche, il relit les events sur disque et en extrait les autres champs.

Champs stockés dès l'indexation : les méta-champs host, source, sourcetype, index et les champs internes _time et _raw (l'event brut).

Les composants

ComposantRôle
ForwarderInstance qui envoie des données à une autre instance Splunk (installé sur les machines à surveiller).
IndexerTransforme la donnée brute en events, les stocke dans un index et répond aux recherches (les search peers).
Search HeadReçoit les recherches des utilisateurs, les distribue aux indexers et fusionne les résultats. S'il ne fait que ça : dedicated search head.

La recherche distribuée sépare la couche recherche/présentation de la couche indexation, pour monter en charge horizontalement.

Les knowledge objects que tu vas créer

Report (recherche sauvegardée), Dashboard (panneaux), Alert (déclenchée sur condition), Lookup (enrichissement depuis un CSV), Data Model (pour Pivot), Tag, Event type.

À retenir

Chaque event a toujours : _time, host, source, sourcetype, index. Forwarder → Indexer → Search Head.

Vérifie-toi

Quelle est la différence entre source et sourcetype ?
La source est l'origine précise (le fichier /var/log/secure), le sourcetype est le format de la donnée (linux_secure). Plusieurs sources peuvent avoir le même sourcetype.
Quels champs existent dès l'indexation ?
host, source, sourcetype, index, plus les internes _time et _raw.
Quel composant fusionne les résultats de plusieurs indexers ?
Le Search Head.

Installer et démarrer Splunk

Sources : module 3, Notes_TP1_Prof.md

Installation sous Linux (pour comprendre)

# Paquet .deb (en root)
apt install ./splunk-10.x.x-xxxx-linux-amd64.deb

# ou archive .tgz
sudo tar xvzf splunk.tgz -C /opt

# Répertoire par défaut
/opt/splunk/bin

Démarrer et arrêter (à savoir pour le TP)

Splunk ne doit pas tourner en root et il ne faut pas modifier les droits des répertoires. On le lance avec l'utilisateur splunk :

# Vérifier / créer l'utilisateur et le groupe si besoin
sudo groupadd splunk
sudo useradd -g splunk -m splunk

# Premier démarrage (création du compte admin)
sudo -H -u splunk /opt/splunk/bin/splunk start --accept-license

# Ensuite
sudo -H -u splunk /opt/splunk/bin/splunk start
sudo -H -u splunk /opt/splunk/bin/splunk stop
sudo -H -u splunk /opt/splunk/bin/splunk restart
sudo -H -u splunk /opt/splunk/bin/splunk status

Au premier démarrage, Splunk demande un nom d'administrateur et un mot de passe d'au moins 8 caractères, génère les certificats, vérifie les ports puis les index par défaut.

Les ports

PortUsage
8000Interface web Splunk Web : http://127.0.0.1:8000
8089Port de management (splunkd, API REST)
8191KV Store
8065App server (local, 127.0.0.1)
9997Réception des données des forwarders (convention, à configurer)

Les rôles et la création d'un utilisateur

  • admin : tout, dont Add Data et la gestion des utilisateurs.
  • power : rechercher, créer et partager des knowledge objects, recherches temps réel. C'est le rôle utilisé dans les labs.
  • user : rechercher et créer ses propres objets.
  1. Settings → Access controls (ou Settings → Users dans les versions récentes).
  2. Users → Add new (New User).
  3. Username uname, mot de passe 5p1unkbcup (valeurs du lab), fuseau horaire.
  4. Dans Assign to roles : retirer user, ajouter power.
  5. Décocher Require password change on first login, puis Save.
Pièges
  • Lancer Splunk en root ou faire un chown sur /opt/splunk.
  • Oublier que Add Data n'apparaît qu'avec le compte admin.
  • Splunk ne permet pas de récupérer un mot de passe admin perdu.

04

Rechercher

Sources : modules 5 et 7, guide de référence

La structure d'une recherche SPL

SPL = Search Processing Language. Avant le premier pipe, il y a une commande search implicite qui va chercher les events dans l'index. Chaque | envoie le résultat à la commande suivante.

termes de recherche | commande1 arguments | commande2 arguments ...

Une recherche est faite de : termes de recherche, commandes, fonctions, arguments et clauses (by, as).

Les termes de recherche

  • Mots-clés : error. Insensibles à la casse.
  • Joker * : fail* trouve fail, failed, failure.
  • Phrase exacte entre guillemets : "port 22".
  • Booléens AND, OR, NOT, toujours en majuscules. AND est implicite entre deux termes.
  • Ordre d'évaluation : NOT, puis OR, puis AND. Les parenthèses forcent l'ordre.
error OR fail*
fail* AND password "port 22"
(index="main" OR index="_internal") error
Piège du module 5

fail* password 22 renvoie tous les events contenant « 22 » n'importe où (heure, PID…). Pour le port SSH il faut la phrase "port 22".

L'écran de recherche

  • Résultats en ordre chronologique inverse (les plus récents d'abord), termes surlignés.
  • Time range picker, search mode, timeline, paginator (20 par page par défaut), Fields sidebar.
  • Cliquer une valeur dans un event : Add to search, Exclude from search, New search.
  • Onglets : Events, Patterns, Statistics, Visualization.

La timeline

  • Survoler une colonne : nombre d'events et période, sans filtrer.
  • Cliquer ou glisser sur des barres : filtre les résultats sans relancer la recherche.
  • Zoom to Selection : réduit la période et relance la recherche. Zoom Out : élargit et relance. Deselect : revient aux résultats d'origine.
  • Un pic d'échecs de connexion au même moment peut signaler une attaque.

Le temps

Unités : s secondes, m minutes, h heures, d jours, w semaines, mon mois, y années. Le @ arrondit vers le bas (snap).

earliest=-1d@d latest=-1h@h error
# à 09:37:12, -30m@h donne 09:00:00 ; à 11:59, @h donne 11:00 (pas 12:00)
# @w0 = dimanche, @w1 = lundi

Les modes de recherche

Fast
Privilégie la vitesse. Pas d'extraction de champs inutiles.
Smart
Par défaut. Équilibre vitesse et complétude.
Verbose
Privilégie la complétude. Donne accès aux events même avec une commande statistique.

Les jobs

  • Chaque recherche est un job. Barre de job : Pause/Resume, Stop (finalise), Job menu, Share, Print, Export.
  • Durée de vie par défaut : 10 minutes, extensible à 7 jours. Pour garder plus longtemps : planifier un rapport.
  • Permissions de lecture : Private par défaut, ou Everyone. Réglage dans Job → Edit Job Settings.
  • Share fait tout d'un coup : lecture pour tous, 7 jours, lien partageable.
  • Export : Raw Events (texte), CSV, XML, JSON. Coûteux en mémoire pour de gros résultats.
  • Activity → Jobs : jobs des 10 dernières minutes et jobs prolongés. Rouvrir un job ne relance pas la recherche.
  • Search History : les chaînes de recherche (pas les résultats), gardées longtemps, filtrables.
À retenir

Opérateurs en MAJUSCULES, AND implicite, phrase entre guillemets, @ arrondit vers le bas, mode Smart par défaut, job : 10 min → 7 jours, Private → Everyone.

Vérifie-toi

Que fait un clic-glisser sur la timeline ?
Il filtre les résultats affichés sur la période sélectionnée sans relancer la recherche. Zoom to Selection, lui, relance.
Durée de vie par défaut d'un job, et maximum via Edit Job Settings ?
10 minutes, extensible à 7 jours.
Quels formats d'export sont proposés ?
Raw Events, CSV, XML, JSON.
Quel mode permet de voir les events derrière un stats ?
Verbose.

Les champs

Sources : modules 6 et 7

La barre latérale des champs

Selected Fields
Affichés sous chaque event. Par défaut : host, source, sourcetype.
Interesting Fields
Présents dans au moins 20 % des events retournés.
All Fields
Lien pour voir tous les champs découverts, y compris les non intéressants.

Devant chaque champ : a = valeurs alphanumériques, # = valeurs majoritairement numériques. Le nombre à droite = nombre de valeurs distinctes.

Cliquer sur un champ ouvre une fenêtre avec ses 10 valeurs les plus fréquentes, des raccourcis de rapports (Top values, Rare values, Events with this field…), et Selected Yes/No pour l'afficher sous chaque event. Cliquer une valeur l'ajoute à la recherche.

Chercher avec des champs

index=main sourcetype=access_combined_wcookie action=purchase
status!=200
src_port>1000 src_port<4000
clientip="202.201.1.0/24"
user=*
sourcetype=access* (referer_domain=*.cn OR referer_domain=*.hk)
  • Noms de champs sensibles à la casse, valeurs non : host=www3 et host=WWW3 marchent, HOST=www3 ne marche pas.
  • Splunk comprend la notation CIDR pour les IP.
  • Opérateurs : = != < <= > >=. champ=* = le champ existe.
  • Chercher par champ est plus précis : status=404 ne confond pas avec un indicatif téléphonique 404.

!= et NOT, la question classique

RechercheRenvoie
status!=200Events où status existe et est différent de 200.
NOT status=200Pareil, plus tous les events qui n'ont pas de champ status.

Les résultats de != sont un sous-ensemble de ceux de NOT. Ils sont identiques seulement si le champ existe toujours (ex. status dans access_combined).

Exercice du module 6

index=main sourcetype=access_combined_wcookie action=purchase status!=200
Résultat attendu

1 301 achats terminés en erreur (vérifié sur tes données). Un statut supérieur à 200 veut dire que l'achat n'a pas abouti.

Vérifie-toi

À partir de quel pourcentage un champ est-il « interesting » ?
20 % des events retournés.
Quels sont les selected fields par défaut ?
host, source, sourcetype.
Status=200 fonctionne-t-il ?
Non : les noms de champs sont sensibles à la casse. status=200 fonctionne. Les valeurs, elles, ne le sont pas.
Pourquoi NOT status=200 renvoie-t-il plus de résultats que status!=200 ?
Parce qu'il inclut aussi les events qui n'ont pas de champ status (ex. les logs linux_secure).

Commandes de base

Sources : modules 7 et 8

CommandeRôleExemple
searchFiltrer après un pipe| search EventCode=100
fieldsGarder (+, défaut) ou retirer (-) des champs. Accélère la recherche.| fields action, JSESSIONID
| fields - host, ip
tableAfficher un tableau avec les colonnes dans l'ordre donné| table JSESSIONID, action
renameRenommer un champ. Guillemets si espaces.| rename JSESSIONID as UserSessions
sortTrier : croissant par défaut, - pour décroissant| sort -count
| sort ip, -url

Le lab 8, étape par étape

Scénario : le marketing veut la liste des sessions avec un achat réussi.

index=main sourcetype=access_combined_wcookie action=purchase status=200
# le champ file vaut success.do (achat traité) ou error.do (erreur)
index=main sourcetype=access_combined_wcookie action=purchase status=200 file=success.do
... | fields action, JSESSIONID, status
... | table action, JSESSIONID, status
... | table JSESSIONID, action, status
... | table JSESSIONID, action, status | rename JSESSIONID as UserSessions
... | table JSESSIONID, action, status | rename JSESSIONID as UserSessions | sort UserSessions

Version finale (dedup le plus tôt possible) :

index=main sourcetype=access_combined_wcookie action=purchase status=200 file=success.do
| dedup JSESSIONID
| table JSESSIONID
| rename JSESSIONID as UserSessions
Pièges
  • Après un rename, le champ s'appelle autrement : sort JSESSIONID ne marche plus, il faut sort UserSessions.
  • fields ne met pas en forme, table si. Avec table, les résultats passent dans l'onglet Statistics.
  • Bonne pratique : dedup le plus tôt possible, filtres avant le premier pipe.

Vérifie-toi

Comment trier par ordre décroissant ?
En mettant un moins devant le champ : | sort -count.
Différence entre fields et table ?
fields garde ou retire des champs (performance) sans changer l'affichage des events. table produit un tableau avec les colonnes dans l'ordre indiqué.
Comment retirer les champs host et ip ?
| fields - host, ip
07

Commandes transformantes

Sources : module 9, guide de référence

Une commande transformante transforme les events en tableau statistique. Ce sont elles qui alimentent les onglets Statistics et Visualization : top, rare, stats, chart, timechart. La doc Splunk classe aussi table parmi elles.

top et rare

  • top : valeurs les plus fréquentes. rare : les moins fréquentes.
  • Colonnes produites : le champ, count, percent. 10 lignes par défaut.
  • Arguments : limit=5, showperc=false, showcount=false, et la clause by.
index=main sourcetype=access_combined_wcookie status=200 file=success.do
| top productId limit=5 showperc=false

index=main sourcetype=access_combined_wcookie status=200
| rare file by date_month

stats et ses fonctions

FonctionCe qu'elle calcule
countNombre d'events (ou d'occurrences d'un champ)
dc(X)Distinct count : nombre de valeurs différentes
sum(X)Somme
avg(X)Moyenne
min(X) / max(X)Minimum / maximum (ordre alphabétique si non numérique)
median, mode, range, stdev, perc95(X)Médiane, valeur la plus fréquente, max − min, écart type, percentile
list(X)Toutes les valeurs, avec doublons, dans l'ordre des events
values(X)Valeurs distinctes, triées par ordre alphabétique
earliest(X) / latest(X)Première / dernière valeur dans le temps

as renomme le résultat (guillemets s'il y a des espaces), by regroupe.

Toutes les requêtes du lab 9

# 1. Les 5 produits les plus vendus
index=main sourcetype=access_combined_wcookie status=200 file=success.do | top productId limit=5 showperc=false

# 2. Fichiers les moins consultés
index=main sourcetype=access_combined_wcookie status=200 | rare file by date_month

# 3. Ajouts au panier et achats
index=main sourcetype=access_combined_wcookie file=success.do OR file=cart.do status=200
| stats count as Transactions by file | rename file as Function

# 4. Sessions par IP
index=main sourcetype=access_combined_wcookie | stats dc(JSESSIONID) as Logins by clientip | sort -Logins

# 5. Bande passante par fichier
index=main sourcetype=access_combined_wcookie status=200 | stats sum(bytes) as TotalBytes by file | sort file

# 6. Requêtes SQL les plus lentes
index=main sourcetype=db_audit | stats avg(Duration) as "time to complete" by Command | sort -"time to complete"

# 7. Navigateurs utilisés
index=main sourcetype=access_combined_wcookie | stats list(useragent)
index=main sourcetype=access_combined_wcookie | stats values(useragent) as "Agents used" count as "Times used" by useragent
| table "Agents used", "Times used"
Résultats attendus (vérifiés sur tes fichiers)
  • Produit le plus vendu : WC-SH-G04 (1 360 ventes), puis DB-SG-G01 et DC-SG-G02.
  • Fichiers rares : api, account, userlist, passwords.pdf. Ce sont ces fichiers qui inquiètent la sécurité.
  • IP avec le plus de sessions : 87.194.216.51.
  • Fichier avec le moins de bande passante : api.
  • Requêtes SQL les plus lentes : des SELECT * avec INNER JOIN sur la table creditcards (~10 000 ms).
Pièges
  • file=success.do OR file=cart.do status=200 fonctionne parce que OR est évalué avant AND.
  • sort -"time to complete" : le moins se met devant les guillemets.
  • Après un stats, seuls les champs calculés et ceux du by existent encore.

Vérifie-toi

Combien de lignes top renvoie-t-il par défaut, et comment cacher le pourcentage ?
10 lignes. showperc=false.
Différence entre list() et values() ?
list garde toutes les valeurs, doublons compris, dans l'ordre des events. values garde les valeurs distinctes, triées alphabétiquement.
Que compte dc(JSESSIONID) ?
Le nombre de sessions différentes.
Écris la requête : nombre d'échecs SSH par utilisateur, du plus grand au plus petit.
index=main sourcetype=linux_secure "Failed password" | stats count by user | sort -count. Sur tes données, root arrive en tête.
08

Rapports et dashboards

Source : module 10

Les rapports (reports)

Un rapport est une recherche sauvegardée (ou un pivot). On peut le lancer à la demande, le planifier, déclencher des alertes et l'ajouter à un dashboard.

  1. Lancer la recherche, puis Save As → Report (au-dessus du sélecteur de temps).
  2. Donner un titre (ex. 403_by_clientip), Save.
  3. Permissions : afficher pour Owner / App / All apps, Run as Owner ou User, lecture/écriture par rôle (ex. Everyone en lecture).
  4. Retrouver le rapport dans le menu Reports. Cliquer le titre le lance.
index=main sourcetype=access_combined_wcookie status=403
| stats count as attempts by clientip
| sort -attempts
Résultat attendu

L'IP avec le plus de tentatives sur des pages interdites (403) : 73.202.92.7, avec 100 tentatives.

Les dashboards

Un dashboard est fait de panneaux (panels), chacun lié à une recherche, un rapport ou un pivot.

  1. Lancer une recherche transformante, onglet Visualization, choisir le graphique (Column Chart, Single Value…).
  2. Save As → Dashboard Panel.
  3. Dashboard New (titre, ex. Sales Dashboard) ou Existing. Donner un Panel Title.
  4. View Dashboard. Pour réorganiser : Edit, glisser le panneau par sa barre, Save.
  5. En bas d'un panneau : Open in Search, export, refresh.
# Panneau « Product Sales » (Column Chart)
index=main sourcetype=access_combined_wcookie file=success.do status=200 | stats count by productId

# Panneau « Total Units Sold » (Single Value)
index=main sourcetype=access_combined_wcookie file=success.do status=200 | stats count
Résultat attendu

Total des unités vendues : 16 139.

Choisir la bonne visualisation

  • Column / Bar chart : comparer des catégories (ventes par produit).

Planifier rapports et alertes

Cours du parcours : Scheduling Reports & Alerts

Planifier un rapport

Un rapport planifié s'exécute tout seul à intervalle régulier. C'est aussi le moyen de garder des résultats plus de 7 jours, et il est indispensable pour envoyer un rapport par mail.

  1. Reports → ligne du rapport → Edit → Edit Schedule, cocher Schedule Report.
  2. Schedule : Run every hour, day, week, month, ou Run on Cron Schedule.
  3. Time Range : la période couverte à chaque exécution (ex. Last 24 hours pour un rapport quotidien).
  4. Schedule Priority : Default, Higher, Highest. Sert quand beaucoup de recherches tournent en même temps.
  5. Schedule Window : marge pendant laquelle Splunk peut retarder l'exécution pour lisser la charge (No window, Auto ou une durée).
  6. Trigger Actions : Send email, Run a script, Log event, Webhook, Output results to lookup…

La syntaxe cron

Cinq champs : minute heure jour-du-mois mois jour-de-semaine (0 = dimanche).

CronSignification
0 * * * *Toutes les heures, à la minute 0
*/15 * * * *Toutes les 15 minutes
30 6 * * 1-5À 6 h 30 du lundi au vendredi
0 0 1 * *À minuit le 1er de chaque mois

Autres options d'un rapport

  • Permissions : Private (Owner), This app only (App), All apps (Global), avec lecture et écriture par rôle.
  • Run as Owner / User : avec quelles permissions de données le rapport tourne.
  • Embed : intégrer un rapport planifié dans une page web externe.
  • Acceleration : précalcul des résultats, possible seulement si la recherche contient une commande transformante.

Alertes planifiées et temps réel

ScheduledReal-time
ExécutionÀ intervalle (cron)En continu
CoûtFaibleÉlevé : à réserver aux cas urgents
DéclenchementNumber of Results, Hosts, Sources ou Custom, comparé à un seuilPer-Result, ou nombre de résultats dans une fenêtre glissante (ex. 1 minute)
  • Trigger Once : une alerte par exécution. For each result : une alerte par résultat.
  • Throttle : ignorer les déclenchements suivants pendant une durée, éventuellement par valeur de champ.
  • Custom condition : une recherche appliquée aux résultats, ex. search count > 10.
  • Les alertes déclenchées (Add to Triggered Alerts) expirent après 24 heures par défaut. Cette durée est réglable.
  • Dans l'email, on peut utiliser des tokens comme $name$ (nom de l'alerte) ou $result.champ$.

Travailler avec le temps

Cours du parcours : Working with Time

Comment Splunk stocke le temps

  • _time est stocké en epoch (secondes depuis le 1/1/1970 UTC). Il est affiché dans le fuseau horaire de l'utilisateur, réglé dans les préférences du compte.
  • Splunk extrait l'horodatage de l'event à l'indexation. S'il n'en trouve pas, il prend l'heure d'indexation.
  • Les champs date_* (date_hour, date_mday, date_month, date_wday, date_year, date_minute, date_zone) sont tirés du texte brut de l'event, sans conversion de fuseau. Ils n'existent que si l'event contient un horodatage.

Les modifieurs dans la recherche

  • earliest et latest écrits dans la recherche prennent le dessus sur le sélecteur de temps.
  • Le @ arrondit vers le bas : @d minuit, @h début d'heure, @w1 lundi, @mon 1er du mois.
  • earliest=-7d@d latest=@d = les 7 jours complets avant aujourd'hui.
  • latest=now = maintenant. Un epoch fonctionne aussi : earliest=1690416000.

Grouper et comparer dans le temps

# Compter par tranche d'1 heure
... | timechart span=1h count

# Découper _time soi-même puis faire un stats
... | bin _time span=1d | stats count by _time, status

# Comparer les jours entre eux (chaque jour devient une série)
... | timechart span=1h count | timewrap 1d

# Activité par heure de la journée, tous jours confondus
... | stats count by date_hour

Formater et convertir

FonctionSensExemple
strftime(X, format)epoch → texteeval jour=strftime(_time,"%d/%m/%Y")
strptime(X, format)texte → epocheval t=strptime(Time,"%d/%b/%Y %H:%M:%S")
relative_time(X, "mod")epoch décalérelative_time(now(),"-1d@d")
now()Heure de lancement de la rechercheeval age=now()-_time

Formats courants : %Y année, %m mois, %d jour, %H heure 00-23, %M minutes, %S secondes, %b mois abrégé (Jan), %a jour abrégé (Sun), %A jour complet, %Z fuseau.

Pour afficher un champ de temps lisible dans un tableau : | eval Heure=strftime(_time,"%H:%M:%S") ou | convert ctime(_time).

Vérifie-toi

Le sélecteur dit « Last 24 hours » et la recherche contient earliest=-7d. Qui gagne ?
La recherche : earliest/latest dans le SPL prennent le dessus sur le sélecteur.
date_hour tient-il compte du fuseau de l'utilisateur ?
Non, il est tiré du texte brut de l'event. _time, lui, est affiché dans le fuseau de l'utilisateur.
Quelle fonction transforme un texte en epoch ?
strptime (p comme parse). strftime fait l'inverse (f comme format).
À quoi sert timewrap ?
À superposer des périodes : par exemple chaque jour devient une courbe, pour comparer aujourd'hui à hier.

Sous-recherches et optimisation

Cours du parcours : Leveraging Lookups and Subsearches, Search Optimization

Les sous-recherches

  • Entre crochets [ ], exécutée avant la recherche principale.
  • Son résultat est converti en conditions : (champ="a") OR (champ="b").
  • Limites par défaut : 10 000 résultats et 60 secondes. Au-delà, les résultats sont tronqués sans erreur bloquante.
  • return renvoie N valeurs (return 5 clientip, ou return $clientip pour la valeur seule). fields sert aussi à ne renvoyer que le champ utile.
# Toutes les actions web des 3 IP qui ont le plus de 403
index=main sourcetype=access_combined_wcookie
  [ search index=main sourcetype=access_combined_wcookie status=403
    | top limit=3 clientip | fields clientip ]
| stats count by clientip, action

# Exclure ce qu'une sous-recherche renvoie
index=main sourcetype=access_combined_wcookie NOT [ | inputlookup ip_autorisees.csv | fields clientip ]

Quand c'est possible, on préfère un stats ou un lookup à une sous-recherche : c'est plus rapide et sans limite.

Les types de commandes

TypeExemplesOù elles tournent
Generatingsearch (implicite), inputlookup, makeresults, tstatsDébut de recherche. Commencent par | sauf search.
Streamingeval, where, rename, fields, rex, lookupEvent par event, sur les indexers. Rapides.
Transformingstats, chart, timechart, top, rareSur le search head, ont besoin de tous les events.

Les règles d'optimisation

  1. Période la plus courte possible.
  2. Toujours index, sourcetype et si possible host/source.
  3. Filtrer avant le premier pipe plutôt qu'avec | search.
  4. Inclure plutôt qu'exclure : status=404 OR status=500 est plus efficace que NOT status=200.
  5. Éviter les jokers en début de terme (*error).
  6. fields tôt pour réduire les données. Commandes streaming avant les commandes transformantes.
  7. Mode Fast quand on n'a pas besoin de tous les champs.

Le Job Inspector

Job → Inspect Job. Il affiche le temps passé dans chaque partie de la recherche (Execution costs), le nombre d'events scannés et retournés, et le search.log. Si beaucoup d'events sont scannés pour peu de résultats, la recherche n'est pas assez précise avant le premier pipe.

Vérifie-toi

Quelles sont les limites par défaut d'une sous-recherche ?
10 000 résultats et 60 secondes.
Pourquoi NOT status=200 est-il moins efficace que status=404 OR status=500 ?
Pour exclure, Splunk doit d'abord récupérer tous les events puis les filtrer. Inclure lui permet de ne lire que ce qui correspond.
Où voir combien d'events une recherche a scannés ?
Dans le Job Inspector (Job → Inspect Job).
Citer une commande génératrice.
inputlookup, makeresults, tstats, ou search implicite.

Report, alert, dashboard, data modelDéjà vus dans les chapitres 8, 9 et 11.

Ordre d'application à la recherche

Field extractions→Field aliases→Calculated fields→Lookups→Event types→Tags

Conséquence : un calculated field ne peut pas utiliser un champ venant d'un lookup, car le lookup est appliqué après. Un alias, lui, peut servir d'entrée à un lookup.

Exemples

# Créer un event type : lancer la recherche puis Save As → Event Type
index=main sourcetype=linux_secure "Failed password"

# L'utiliser
eventtype=echec_ssh | stats count by user

# Chercher par tag
tag=serveur_web

# Appeler une macro (définie dans Settings → Advanced search → Search macros)
`web_achats` | top productId

Permissions et nommage

  • Trois niveaux de partage : Private (seulement le créateur), This app only (l'app), All apps (global). Droits de lecture et d'écriture par rôle.
  • Un utilisateur user crée des objets privés. Il faut le rôle power ou admin pour les partager.
  • Un objet orphelin est un objet dont le propriétaire a été supprimé. L'admin doit le réattribuer (Reassign Knowledge Objects).
  • Convention de nommage conseillée par Splunk : Groupe_Type_Plateforme_Catégorie_Temps_Description, ex. SOC_Alert_Linux_Auth_RT_EchecsRoot.

Vérifie-toi

Dans quel ordre Splunk applique-t-il extractions, alias, calculated fields, lookups, event types et tags ?
Extractions → alias → calculated fields → lookups → event types → tags.
Un event type peut-il contenir | stats ?
Non : un event type ne peut contenir ni pipe ni sous-recherche.
Comment appelle-t-on une macro dans une recherche ?
Entre accents graves : `nom_macro`, ou `nom_macro(arg)` avec des arguments.
Différence entre field alias et calculated field ?
L'alias donne un autre nom à un champ existant. Le calculated field crée une nouvelle valeur avec une expression eval.
Quels sont les trois niveaux de partage d'un knowledge object ?
Private, This app only, All apps (global).

Synthèse de tout le cours

La checklist

  1. Démarrer Splunk : sudo -H -u splunk /opt/splunk/bin/splunk start, puis ouvrir http://127.0.0.1:8000.
  2. Se connecter en admin (Add Data n'existe qu'en admin).
  3. Ingérer chaque fichier avec le bon sourcetype et le host demandé.
  4. Créer l'utilisateur power si c'est demandé.
  5. Dans Search & Reporting : mettre All time.
  6. Toujours commencer par index=main sourcetype=….
  7. Sauvegarder ce qui est demandé : rapport, panneau de dashboard, lookup, alerte, avec les noms exacts de l'énoncé.

Les requêtes modèles

# Achats réussis
index=main sourcetype=access_combined_wcookie status=200 file=success.do

# Top N
... | top productId limit=5 showperc=false

# Compter par champ et trier
... | stats count as Total by clientip | sort -Total

# Valeurs distinctes
... | stats dc(JSESSIONID) as Logins by clientip

# Somme et moyenne
... | stats sum(bytes) as TotalBytes by file
index=main sourcetype=db_audit | stats avg(Duration) as "time to complete" by Command

# Tableau propre
... | dedup JSESSIONID | table JSESSIONID | rename JSESSIONID as UserSessions

# Lookup
| inputlookup products_lookup
... | lookup products_lookup productId OUTPUT product_name as ProductName

# Alerte de connexion
index=_audit action="login attempt" info=failed user=admin
